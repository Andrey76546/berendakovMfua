# Лабораторная работа «Normalization №2»

## 1. Оригинальное задание

Работа выполнена по инструкции преподавателя: [Normalization_2.md](https://github.com/rurewa/imfua/blob/main/content/Courses/Basics_database_design/content/bd/Normalization_2.md).

## 2. Цель работы

Создать ненормализованный набор продаж, на реальных запросах показать аномалии обновления, вставки и удаления, привести данные к 3NF, перенести их через `INSERT ... SELECT`, проверить сохранность и целостность информации, а затем сохранить дампы, журнал действий и визуальные подтверждения.

## 4. Создание базы и исходной таблицы

Сценарий [sql/00_create_source.sql](sql/00_create_source.sql) создаёт отдельную БД `sales_norm_2`, таблицу `sales_unnormalized` строго по практической части задания и вставляет без изменений все 10 строк преподавателя.

Сценарий выполнен в реальном MySQL-сеансе командой вида:

```bash
docker exec normalization-2-mysql mysql -uroot \
  --default-character-set=utf8mb4 --show-warnings -vvv \
  -e "source /lab/sql/00_create_source.sql"
```

MySQL подтвердил: `10` строк, `0` дубликатов, `0` предупреждений; исходная сумма — `80000.00`. Полный вывод: [evidence/01_source_creation.txt](evidence/01_source_creation.txt).

## 5. Демонстрация трёх аномалий

Сценарий [sql/01_demonstrate_anomalies.sql](sql/01_demonstrate_anomalies.sql) сначала создаёт тестовую копию `sales_unnormalized_anomaly_demo`. Каждая опасная операция выполняется внутри отдельной транзакции и завершается `ROLLBACK`; после проверки копия удаляется. Исходные данные не меняются.

1. **Аномалия обновления.** Изменение города только в одной из трёх строк клиента `101` породило два города (`Тверь` и `Москва`) для одного клиента; `COUNT(DISTINCT client_city) = 2`.
2. **Аномалия вставки.** В исходной структуре нет отдельной сущности клиента. Поскольку DDL преподавателя допускает `NULL`, MySQL принимает нового клиента только как неполную строку с `NULL` в полях продажи и товара. Это физически допустимо, но семантически является повреждённой записью продажи.
3. **Аномалия удаления.** Удаление всех трёх строк клиента `102` уменьшило число доступных строк о нём с `3` до `0`, то есть вместе с продажами исчезли сведения о клиенте.

После всех откатов исходная таблица сохранила `10` строк и сумму `80000.00`. Фактический вывод: [evidence/02_anomalies.txt](evidence/02_anomalies.txt).

## 6. Нормализация до третьей нормальной формы

Исходная строка смешивает три сущности и связь между ними. Сценарий [sql/02_create_3nf.sql](sql/02_create_3nf.sql) создаёт четыре требуемые таблицы:

| Таблица | Первичный ключ | Назначение |
|---|---|---|
| `clients` | `client_id` | единственное место хранения имени и города клиента |
| `products` | `product_id` | единственное место хранения названия и цены товара |
| `sales` | `sale_id` | дата продажи и ссылка на клиента |
| `sale_items` | `(sale_id, product_id)` | состав продажи и количество товара |

Связи: `clients 1:N sales`, `sales 1:N sale_items`, `products 1:N sale_items`. Внешние ключи используют `ON UPDATE CASCADE` и `ON DELETE RESTRICT`; цена ограничена `unit_price >= 0`, количество — `quantity > 0`. Реальное создание таблиц: [evidence/03_create_3nf.txt](evidence/03_create_3nf.txt).

Такая структура соответствует 3NF: неключевые атрибуты клиента и товара хранятся только рядом со своими ключами, а `sale_items.quantity` зависит от полного составного ключа.

## 7. Перенос информации через `INSERT ... SELECT`

[sql/03_migrate.sql](sql/03_migrate.sql) переносит данные только выборками из `sales_unnormalized`:

- `clients` и `products` — `SELECT DISTINCT`;
- `sales` — `SELECT DISTINCT sale_id, sale_date, client_id`;
- `sale_items` — все исходные пары `sale_id/product_id` и их количество.

Перенос выполнен одной транзакцией и завершён `COMMIT`. MySQL фактически вставил `3`, `5`, `6` и `10` строк без дубликатов и предупреждений: [evidence/04_migration.txt](evidence/04_migration.txt).

## 9. Дампы до и после нормализации

Оба файла созданы настоящей утилитой `mysqldump` из контейнера:

```bash
docker exec normalization-2-mysql mysqldump -uroot \
  --default-character-set=utf8mb4 --single-transaction \
  --databases sales_norm_2 > dumps/before_normalization.sql

docker exec normalization-2-mysql mysqldump -uroot \
  --default-character-set=utf8mb4 --single-transaction \
  --databases sales_norm_2 > dumps/after_normalization.sql
```

- [dumps/before_normalization.sql](dumps/before_normalization.sql) — 3576 байт, 1 `CREATE TABLE`, 1 блок `INSERT`;
- [dumps/after_normalization.sql](dumps/after_normalization.sql) — 7596 байт, 5 `CREATE TABLE`, 5 блоков `INSERT`.

Проверка файлов: [evidence/07_dump_validation.txt](evidence/07_dump_validation.txt). Размеры и SHA-256: [evidence/08_artifact_manifest.txt](evidence/08_artifact_manifest.txt). Оба дампа дополнительно восстановлены в чистом временном контейнере: [evidence/10_dump_restore_check.txt](evidence/10_dump_restore_check.txt). Дамп «до» восстановил 1 таблицу, 10 строк и сумму `80000.00`; дамп «после» — 5 таблиц, контрольные количества `10/3/5/6/10` и равные суммы `80000.00`. После проверки удалён только временный контейнер восстановления.

Исходная таблица после успешной проверки намеренно **не удалена**: она является контрольным эталоном для JOIN-сравнения и позволяет повторить проверку. Поэтому итоговый дамп содержит четыре таблицы 3NF и сохранённую исходную таблицу.

## 12. Обнаруженные расхождения в инструкции

1. В начальном списке задач названа таблица `orders_bad`, но практическая часть определяет и заполняет новую таблицу `sales_unnormalized`. В этой работе использован именно новый практический набор из 10 строк; старая лабораторная с `orders_bad` не копировалась и не изменялась.
2. Формулировка «нельзя добавить нового клиента» является логическим ограничением модели. В данном DDL все столбцы nullable, поэтому SQL технически принимает клиента только как неполную строку продажи с множеством `NULL`. Это и показано, а не скрыто, в демонстрации аномалии вставки.
3. В тексте зависимости сформулированы как `client_name → client_city` и `product_name → unit_price`. Имена и названия сами по себе не обязаны быть уникальными. Практическая схема преподавателя содержит идентификаторы, поэтому в 3NF использованы устойчивые зависимости `client_id → client_name, client_city` и `product_id → product_name, unit_price`.

Исходные требования сохранены; ни одно расхождение не использовалось для упрощения работы.
